# Separate edited-review catch-up

The existing 04:00 UTC import/analysis pipeline keeps its selected creation-date window. A separate **review-edits** cron endpoint refreshes already-stored reviews regardless of their original posting date. Google supports [paginated reviews ordered by `updateTime desc`](https://developers.google.com/my-business/reference/rest/v4/accounts.locations.reviews/list); there is no separate edited-only feed or updated-since query parameter. We compare fetched reviews with stored hashes and update only matching records that changed.

The scheduler invokes `/api/cron/review-edits` every five minutes. Each eligible location becomes due once an hour after its previous pass completes. The first pass reads history to establish a baseline and refresh stored old reviews, including attachments. It does not import unknown reviews. Later passes stop at the previous successful run's start time minus a 48-hour overlap, using Google's review update time rather than creation date. Missing or invalid update timestamps cannot prove the cutoff was reached, so paging continues.

Each invocation has a bounded page/time budget. The page token, frozen cutoff, start time and counters are durable in `grm_review_edit_sync`. Large passes continue on the next scheduler invocation. Data, per-review audit history and page advancement commit together. Failure never advances the successful watermark; retry backoff begins at five minutes, and an expired Google cursor restarts safely. The initial history pass can take multiple invocations. Google must expose an edit through its API and timestamp it for subsequent update-window polling to detect it; the overlap accommodates delayed visibility but is not a provider delivery guarantee.

The worker shares the regular pipeline's location lock and locks review rows while saving. It preserves local drafts, approvals and publish state, while refreshing review text, stars, Google reply text and attachment metadata. Edited answered reviews are marked reopened, prompting a person to check the current response. Each changed record has before/after audit details; each completed location pass has counters and a watermark, and failures record their cause. No absence/deletion inference is made from this partial scan.

This job does **not** call AI, generate drafts, rebuild daily summaries or reports, or publish replies. Actual text/rating edits invalidate the affected analysis/summary source data for the existing analysis/view workflow to refresh later. Unchanged text and media-only changes do not initialise legacy content fingerprints or invalidate existing text analysis. Edited public responses still require the explicit [edit and send flow](./EDIT_PUBLISHED_REPLIES.md).

Both cron endpoints require the configured cron bearer secret. Only active workspaces, active Google connections and active locations without a hold are checked. The new schedule requires deployment of both the app and the separate cron service. Pub/Sub is not required for this mechanism.
